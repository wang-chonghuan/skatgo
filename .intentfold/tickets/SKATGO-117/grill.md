## 第一批问题

### Q1. 什么时候记"邀请人"？

- **问题**：工单写"受邀者之后在同一浏览器注册，就记下邀请人"。浏览器里能把他和那张桌联系起来的，只有为了"回到座位"而存的座位凭证。要在他以后任何时候、任何页面注册时都认出来，就得在注册时去读这份存储，用来做归因。按欧盟 ePrivacy 的严格读法，这不是"严格必要"的用途，需要同意弹窗，和"不能引入需要同意弹窗的追踪"冲突。
- **推荐**：只记录"在牌桌页面上注册"的受邀者：局后提示里点注册，或者坐在桌上时从页头登录注册。那一刻页面本来就在用这张桌的座位凭证，不需要新 cookie，也不需要事后去别处读存储。离开牌桌后再注册的，不记。
- **理由**：守住"不加弹窗"；绝大多数注册会发生在刚打完、看到提示的时候。
- **决定**（agent 代为决定，人授权）：采纳推荐：只记录在牌桌页面上注册的受邀者。更宽的归因要同意弹窗，弹窗伤获客，得不偿失。

### Q2. 只算新注册的账号吗？

- **问题**：受邀者在桌上登录的如果是已有账号，算不算被邀请来的？
- **推荐**：不算。只有账号创建不到 1 小时的（真正新注册的）才记；每个账号只记第一次，以后不改。
- **理由**："邀请人"要回答的是"谁带来了新用户"。老账号不是拉来的。
- **决定**（agent 代为决定，人授权）：采纳推荐：只算创建不到 1 小时的账号，每个账号只记第一次。

### Q3. 邀请人存在哪？

- **推荐**：多人服务的数据库里加一张表 `account_referrals`：新账号、邀请人账号（开桌人）、哪张桌、时间。你要看的时候按 operations.md 的方式查生产库。
- **备选**：写进 Clerk 账号的元数据，在 Clerk 后台点开用户就能看到；但那样数据在外部服务，查"哪个组织者带来了几个人"不方便。
- **理由**：和 `ladder_answers`、`daily_players` 的做法一致，一条 SQL 就能按组织者汇总。
- **决定**（agent 代为决定，人授权）：采纳推荐：多人服务数据库新表 `account_referrals`，与 `ladder_answers`、`daily_players` 同一做法，架构最简。

### Q4. 局后注册提示怎么写、什么时候出现？

- **问题**：工单里的文案是"注册后可以自己开桌、保存战绩"，但私人桌的战绩并不会存进账号，后半句不属实。
- **推荐**：
  - 文案：中文意思是"注册后，你也能开自己的桌子，请朋友来打"；英、德两版同义。
  - 形式：一行字，加一个白色（quiet）的"注册"按钮和一个"不用了"。
  - 时机：未登录的受邀者每局结束时出现在本局比分下方；点"不用了"后，这张桌上不再出现。
- **理由**：不夸大；不抢"下一局"这个主按钮（ui.md：每屏只有一个绿色主按钮）。
- **决定**（agent 代为决定，人授权）：采纳推荐：文案为"注册后，你也能开自己的桌子，请朋友来打"（英、德同义），quiet 注册按钮加"不用了"；每局结束显示，点"不用了"后本桌不再出现。它是获客的转化点，但不抢主按钮。

### Q5. 隐私页要不要加一句？

- **推荐**：加。中文意思是"你在别人的私人桌上注册时，我们会记下是谁的桌子"；英、德两版。
- **理由**：透明，也不需要弹窗。
- **决定**（agent 代为决定，人授权）：采纳推荐：隐私页加一句，说明在别人的私人桌上注册时会记下是谁的桌子。

### Q6. 未登录的人在"和朋友打"页面看到什么？

- **推荐**：在名字表单的位置，显示一句"开桌需要登录（免费）"，加一个绿色的"登录后开桌"按钮，点了弹出 Clerk 的登录窗。和 Tricks 第三题的邀请写法一样，不加锁图标（SKATGO-112）。登录后，原来的名字表单出现。
- **理由**：先告诉人要登录，比点了按钮才弹出登录更不意外；也是站内已有的写法。
- **决定**（agent 代为决定，人授权）：采纳推荐：沿用 Tricks 第三题的登录邀请写法，在名字表单的位置先说明再给登录按钮，不加锁。

### Q7. 部署时的健康检查（与工单建议方案不同）

- **问题**：工单建议把多人服务的 Render 健康检查改成 `/readyz`。但新实例要等旧实例退出、交出房间所有权后才会"就绪"，而 Render 要等新实例"健康"才让旧实例退出：改了以后每次部署都会卡死。
- **推荐**：健康检查保持 `/healthz`。改为：web 发入场票前先问多人服务是否就绪，没就绪就回"稍后再试"，页面自动重试，直到新实例恢复好牌桌。
- **理由**：同样解决"部署后玩家进不来"，又不会卡死部署。
- **决定**（agent 代为决定，人授权）：采纳推荐：健康检查保持 `/healthz`；web 发入场票前先问 `/readyz`，没就绪回 `503 not_ready`，页面自动重试。改成 `/readyz` 会让部署卡死。

### Q8. 发布顺序（与 operations.md 的惯例相反）

- **问题**：这次入场票会带上"开桌还是入座"和开桌人的账号。operations.md 的惯例是两边都改时先发多人服务。
- **推荐**：这次先发 web、再发多人服务。先发 web 时，新票仍是旧版本号，旧的多人服务照常接受；再发多人服务，它才开始要求"开桌票必须带账号"。顺序写进 handoff。
- **理由**：反过来先发多人服务的话，在 web 跟上之前谁都开不了桌。
- **决定**（agent 代为决定，人授权）：采纳推荐：先发 web，再发多人服务，写进 handoff 和 operations.md。

### Q9. 验收里需要登录的那几步，由谁来做？

- **问题**：我不能在 Clerk（外部登录服务）上注册或登录账号，即使是开发用的测试账号也不行。operations.md 写着用 `clerk users create` 建测试账号，这一步我做不了。
- **推荐**：
  - 我来做的：
    - 用接口验证"未登录不能开桌"；
    - 用替身会话测试验证"登录后发的开桌票带账号""老账号不记邀请人"；
    - 用无头 SDK 加本地数据库，验证多人服务这一侧"没有账号的票开不了桌""邀请人入表"；
    - 断线、刷新、重启服务这三种情况的全部检查。
  - 你在验收时做的（我写好逐步说明）：
    - 用开发环境账号登录，开一张桌；
    - 换一个浏览器以受邀者身份进桌，在局后提示里注册；
    - 然后我查表确认邀请人。
  - 这几步在验收记录里标为"由你确认"，不算作我验过。
- **理由**：不违反账号规则，也不把没跑过的检查记成通过。
- **决定**（human，2026-10-19）：不采纳"由你确认"。人：「那只能麻烦你开一个本地的账号和最小代码机制，用来尽最大可能逼真测试了，我拒绝给我添麻烦做这些，这些的自动化是你的责任，不是我的责任」。登录相关的验收改用本地测试账号机制，全部由 agent 自动完成，机制见 Q13。

### Q11. 断线后页面自己重试多久？

- **推荐**：约 2 分钟：间隔 1、2、4、8 秒，之后每 10 秒一次；手机回到前台、网络恢复时立刻再试。超过 2 分钟仍连不上，才显示错误，并给一个"再试一次"按钮。期间牌桌上方一直显示"正在重连"。
- **理由**：一次部署从切流量到新实例恢复牌桌大约几十秒，2 分钟足够；再长就该让人知道出了问题。
- **决定**（agent 代为决定，人授权）：采纳推荐：重试约 2 分钟（1、2、4、8 秒，之后每 10 秒），回到前台或网络恢复时立刻再试；期间显示"正在重连"，超时后报错并给"再试一次"。

## 第二批问题（Q9 的决定带出）

### Q13. 本地测试账号机制怎么做？

- **问题**：人要求做一个本地账号和最小的代码机制，让 agent 自己把登录相关的验收跑完。它会进入产品代码，必须保证线上不可能被打开。
- **推荐**：
  - **服务器端**：只在两种情况同时成立时才认"测试账号"：一是环境变量 `SKATGO_TEST_ACCOUNTS=1`，这个变量只写在本机的 `app/.env`，生产环境变量清单里没有；二是请求本身发到 localhost 或 127.0.0.1。认的方式是读一个 cookie `skatgo_test_account`，值是账号名加创建时间（如 `test_host.1760000000000`）。
  - 认出来时，`session.ts` 的"谁登录了"返回 `test_host` 这样的账号 id，所有服务器接口（开桌票、邀请人、每日赛、Tricks）都照真账号处理；判断"新注册"时用 cookie 里的创建时间，不去问 Clerk。
  - **页面端**：根路由把测试账号交给页面，`useAccount()` 优先用它。页面因此显示"已登录"的样子（名字表单、局后提示的判断等）。Clerk 的登录弹窗本身不测；"注册"这一步由测试脚本写 cookie 代替，再让页面重新读一次账号。
  - **防线**：一个自动测试证明变量没开、或请求不是发到本机时，这个 cookie 被完全忽略；客户端打包检查保证页面代码里没有读环境变量。
  - operations.md 的"登录验收用 Clerk 开发账号"那一行，改成用这个本地机制；engineering.md 写明这个开关和它的两道防线。
- **理由**：
  - 只碰"谁登录了"这一个入口，其他代码不知道测试账号的存在，测到的就是真实的服务器路径；
  - 两道防线都是机器能检查的事实（环境变量清单、请求的主机名），不靠人记得。
- **决定**（agent 代为决定，人授权）：采纳推荐：两道防线（本机环境变量加本机请求），只碰"谁登录了"这一个入口。
